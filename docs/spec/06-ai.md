# AI features

This area covers everything in the application backed by a language model: a
conversational assistant for exploring the repository, a one-shot explanation
of a commit, an automatically drafted commit message, and an agent that
attempts to resolve merge conflicts on its own. All of it is optional — the
application works fully without it — and every feature can be pointed at a
different provider and a different model.

## Concepts

- **Provider**: the source of model responses. Three are supported: a local
  server the user runs on their own machine, and two hosted services reached
  over the network, each needing a stored API key.
- **Chat/agent role vs. task role**: the provider and model used for the
  conversational chat and the conflict resolver are configured together (one
  pair); the provider and model used for the one-shot tasks — explaining a
  commit, drafting a commit message — are configured separately, so a cheap
  model can be used for the small tasks while a more capable one drives the
  conversation.
- **Tool**: a narrow, named capability the model can invoke mid-conversation
  — for example, searching the commit log — with typed arguments and a text
  result it reads back.
- **Run**: one exchange between the user (or the application, for an
  automatic action) and the model, made up of one or more model replies and
  any tool calls in between, up to a fixed step limit.
- **Prompt**: the fixed instructions given to the model before a
  conversation or task starts. Each of the four AI-driven actions has its
  own prompt.

## Providers and keys

Three providers can be configured: a local one reached over HTTP with no
credential needed, and two hosted ones that each require an API key.

The local provider's address is itself configurable (it defaults to the
machine's own loopback address); pointing it at any other host is accepted
but flagged as sending repository content over the network, since it no
longer stays on the machine running the application.

A hosted provider's API key is entered once in settings and stored in the
operating system's own secret store (the platform's keychain or equivalent),
never in the application's own settings file and never in plain text. If the
platform has no usable secret store, saving a key fails outright with an
explicit message — there is no fallback that would write it somewhere
readable. Once stored, the key itself is never sent back to the interface;
only a masked hint (its first few and last few characters) is shown, and a
"Remove" action deletes it from the store.

### Choosing a model

The chat/agent role and the task role each have an independent provider and
model choice. Switching a role's provider clears that role's model unless
the new provider's model list still contains it, in which case it stays
selected; otherwise the first model on the new list is chosen, or none if
the list is empty.

Where the model list comes from depends on the provider:

- The local provider's list is whatever models are currently installed on
  it; there is no other choice possible for it — every one of its models
  runs equally without further configuration.
- A hosted provider's list is fetched live from that provider using the
  stored key. With no key stored, no list is fetched at all; the interface
  shows an explanation ("add a key to see the models") in place of the
  dropdown. If fetching the list fails for a provider that does have a key
  stored (for instance, because the key has since become invalid), that
  failure is shown in place of the dropdown too, distinct from the
  no-key case.

### What happens with no key or no model configured

Every AI-driven action first resolves the configured provider and model for
its role. If a hosted provider has no key stored, the action fails
immediately with a message naming the provider and telling the user to add a
key in settings, rather than attempting a network call that would fail
anyway. An empty model name is rejected the same way settings themselves are
rejected: settings cannot be saved with an empty chat or task model to begin
with, so this case chiefly protects a call made through another surface (for
instance, an automatic action) against a settings file left in an
inconsistent state.

## The chat panel

The chat panel holds one conversation per repository, persisted to disk
across restarts. Only one conversation is kept per repository — there is no
notion of multiple named threads — and starting a new conversation replaces
the saved one outright (it cannot be recovered afterwards).

Sending a message appends it to the conversation and starts a run: the
model's reply streams in as it is produced, interleaved with any tool calls
it makes and their results, until it produces a final answer with no further
tool calls, or a fixed step limit is reached, at which point the run ends
with a note that the limit was reached. Only one run can be active for a
repository at a time; the same slot is shared with the commit-explanation
action and the conflict resolver, so at most one of chat, an explanation or a
conflict-resolution run can be in progress for a given repository at once. A
running exchange can be stopped by the user; a stopped answer is kept exactly
as far as it got, marked as stopped, rather than discarded.

The panel only takes messages once the provider configured for the
chat/agent role can answer: for the local provider, it must be reachable and
have the configured chat model installed; for a hosted provider, it must have
a key stored — the local provider's state does not matter then. Otherwise the
panel shows what is missing, with a way into settings, and the composer is
disabled. This is checked again when the panel opens, when the app regains
focus and when settings close.

Once an answer has text and is no longer being written, a row beneath it
offers a copy button (the answer's text as written, markdown included), how
long ago it finished ("2m ago", kept current while the panel is open, the
exact time on hover) and the provider and model that produced it
("Anthropic · claude-opus-5"): the chat role's pair for a typed message and
for the conflict resolver, the task role's pair for an explanation. The time,
provider and model are stored with the answer, so they still show what was
used then after the settings change or the app restarts; an answer stored
before they were recorded shows only what it has, never a guess.

In the bar below the message box, opposite Send, a picker shows the chat role's model and
changes it. It offers the local provider's installed models while it is
running, and the listed models of each hosted provider that has a key; a
provider with nothing to offer is left out, and the menu ends with a way into
settings. Choosing a model changes the same chat/agent setting as settings do
— for every repository, not just this conversation — and takes effect from
the next message. The picker is disabled while an answer is running.

A commit can also be explained directly from the log, which asks the same
question a user would type ("explain commit …") and writes the answer into
the same conversation, so the explanation and the ordinary chat share one
history and the user can keep asking about what came back.

Both kinds of explanation first read what the model needs (the commit, its
diff, the blame of the lines) before the question appears in the chat. Until
then the chat shows "Preparing the explanation…" with the Stop button, and
sending is not possible. Stopping at that point cancels the explanation
without adding anything to the conversation, and without an error.

**Explaining lines**: started from the Blame view's menu on a block or a
selected range, the same way a commit explanation is started from the log. The
question stored in the conversation reads "Explain lines 40–58 of path (at
a1b2c3d)" (or "line N" for a single line, or "(working tree)" when the
explanation is of the working-tree version of the file, i.e. rev == ""). The
model is given the lines themselves, the blame of the range, and up to five of
the commits behind them, newest first, each with its message and its diff of
the file; lines that are not committed yet are described by the working-tree
diff instead. It uses the same provider and model as explaining a commit, has
no tools, and takes the repository's chat slot the same way a commit
explanation does, so it is refused while the chat is busy.

Long conversations are trimmed before being sent to the model: only a
bounded number of the most recent messages are kept, never starting midway
through a tool result, and older tool results beyond a smaller, more recent
window are replaced with a placeholder noting they were omitted. This keeps
every request bounded regardless of how long the conversation has run,
without discarding the conversation itself — the trimming only affects what
is sent to the model on the next turn, not what is stored or displayed.

## Read tools

The chat agent can call a fixed set of tools that only read: searching the
commit log by text, author, date range, branch or path; showing one commit's
full message, author, parents and changed files; showing the diff of one file
within a commit; listing the current branch, local branches, remote branches
and tags; listing the commits that touched a given file; and, for a file at a
revision (the current commit by default), which commit last changed each block
of lines — one line per block with its line range, commit, date, author and
subject, optionally for a line range only, and cut after 200 blocks, or fewer
to fit the tool output limit, with a note to narrow the range. None of them can
change a branch, a file, the index or any setting, and they are the only tools
available to a commit explanation started from the log (see "Explaining a
commit" below) — that surface has no write tools at all.

A large result from any tool is cut to a fixed size, with a note that it was
cut, so the model can ask again with narrower arguments instead of the
conversation being crowded out by one huge answer.

A diff a tool returns for a submodule path is the same `--submodule=log`
commit-range summary the Changes view and the details pane show, never a raw
`Subproject commit` line.

The assistant has no access to the embedded terminal (see Terminal): it
never sees anything typed into or printed by a shell tab, and no tool lets it
type into one. Terminal scrollback can hold secrets — tokens, the contents of
a `.env` file printed by `cat` — which is the reason this is not merely an
oversight.

## Write tools, each confirmed by the user

Alongside the read tools, an ordinary chat run (not a commit explanation)
has a second, smaller set of tools that change the repository: staging or
unstaging one or more paths, committing the staged changes (never with
amend), creating a branch, checking out a local or remote branch, pushing a
stash, fetching, pushing, pulling, merging a branch into the current one,
and cherry-picking a single commit onto the current branch. Nothing
destructive is offered this way — no reset, no discard, no deleting a
branch, no amend, no dropping/popping/applying a stash, no force-push, no
rebase (rebase rewrites history, so it stays out of chat's reach even though
cherry-pick, which only adds a commit, is offered). Asked for one of those,
the assistant explains which git command or application action would do it,
rather than attempting anything: it has no tool for it.

The cherry-pick tool takes a single commit (full or abbreviated hash) and
refuses it outright — before any card is shown — for an invalid or unknown
commit, a merge commit, a commit already on the current branch, a detached
`HEAD`, an operation already in progress (merge, rebase, cherry-pick, and so
on), or uncommitted tracked changes in the worktree. Like a pull or merge, a
cherry-pick that ends in conflicts opens the conflict view instead of
failing silently; one that ends up empty because the branch already has
those changes reports that nothing was applied rather than creating an empty
commit.

Every write is something the user asks for and can see, the same as
everywhere else in the application — the approval card described below **is**
the user asking for that specific operation to run, in the same sense that
clicking Commit or Push in the toolbar is. Nothing the assistant proposes
runs without it.

### Proposing a change

When the model calls a write tool, the tool call does not resolve
immediately. First, the arguments are validated and turned into a proposal:
a title and a few lines of detail describing exactly what will happen (the
branch it targets, the commits involved, the message to commit, and so on).
An argument that cannot possibly succeed — an unknown branch, a path not
currently shown as changed, a commit with nothing staged, a push, pull or
merge attempted with a detached `HEAD`, a branch name that is actually a
revision expression such as `main~2` or `main@{u}` — is rejected at this
point with an error the model sees; no card is shown and the user is never
asked to approve something that cannot run.

Once a proposal is built, the chat shows a card with its title and details
and two buttons, Reject and Approve. The run pauses here — no further part
of the model's answer is produced — until the user decides, however long
that takes; there is no timeout. Only one write proposal is pending at a
time, and only one AI run (chat, commit explanation, or the conflict
resolver) can be active per repository regardless, so the composer stays
disabled while a card waits.

Stopping the run (the same Stop control that stops any other run) while a
card is pending counts as a rejection of that card.

If the model asks for several write tools in a single reply — proposing more
than one change before waiting to see the first one's outcome — only the
first is shown normally. Once a write call in that same reply does not end
in success, every later write call in that reply is refused outright,
before it is even turned into a proposal: no card is shown for it. This
only applies within one model reply; a later reply (after the model sees
the result and responds again) is free to propose another write. The
assistant's own instructions ask it to propose one change at a time and
wait, and to stop and ask before proposing another once one has been
rejected, rather than relying on this as the only guard.

### What happens on approval

Approving a card does not simply run what was proposed: the repository is
re-checked first, because time has passed while the user was deciding. The
check compares the repository's current refs and `HEAD` against what they
were when the proposal was built, and — for a commit specifically — also
compares the current set of staged paths. If either has changed, nothing
runs; the model is told the repository changed since this was proposed and
to check its state and propose again.

If the repository still matches, the change runs through the same
application logic the toolbar and views use for the same operation,
including that operation's own per-repository write lock. If another
mutating operation is already running against that repository, the write is
refused with a busy error and nothing happens — the same as if the user had
tried the same action from the toolbar while something else was running.
The write lock itself is not held while the card sits waiting for the user;
only the re-check above stands in for it during that wait.

A pushed branch targets `@{push}` — what a plain push actually goes to,
which can differ from the branch's upstream in a triangular setup — falling
back to the upstream when `@{push}` does not resolve. When the repository's
push mode is configured to push every matching branch rather than the
current one alone, the push proposal is refused outright and the user is
told to push from the toolbar instead, since a plain push in that mode is
not limited to the branch the assistant means.

A pull, merge or cherry-pick that ends in conflicts does not fail silently:
the result names how many files are conflicted and says the conflict view is
now open to resolve them there — the same conflict view any other pull,
merge or cherry-pick leaves open.

Whatever the outcome — the change succeeded, or it was attempted and failed
partway (for instance a branch that was created but could not be switched
to, reported as such rather than as a bare failure) — the repository is
refreshed afterward, the same refresh that follows any other write made
through the toolbar. A refusal before anything was attempted (the
repository changed, or another operation was already running) does not
trigger that refresh, since nothing changed.

### The card itself

A pending card can survive the chat panel being closed and reopened, or the
user switching to another repository and back: reopening a repository's
chat restores its still-pending card rather than leaving the run looking
stuck with nothing to click. Once decided, the card shows its outcome in
place of the buttons.

## The AI commit message

A commit message can be generated for the currently staged changes, using
the task role's provider and model. The prompt is given the list of staged
files and their staged diff (not the unstaged changes — the message
describes only what is being committed), cut to a fixed size budget with a
note when it had to be cut. Generation is refused outright when nothing is
staged.

Three modes control when this happens automatically, chosen in settings:

| Mode | When the message is generated automatically |
|---|---|
| Automatic for local models (default) | Only when the task role's provider is the local one, since that is free to run repeatedly with no cost. |
| Always automatic | Whenever there is something staged and the message box is otherwise empty, regardless of provider. |
| Only when asked | Never automatically; only when explicitly requested. |

In every mode, automatic generation never overwrites anything the user has
already typed into the message box, and it never fires with nothing staged.
Once the user types anything into the box (or the box already holds
generated text), it is treated as "touched" and no longer eligible for
automatic replacement until it is cleared again.

## The AI conflict resolver

Once a merge, a rebase or a cherry-pick is in conflict, a resolve action can
hand the conflict to the model, using the chat/agent role's provider and
model — not the task role's. A rebase with several conflicting steps needs
one run per step. The resolver is not offered for a revert, an applied
patch (`am`) or a stash application; those are left to be resolved by hand.
This is a longer-running agent with a higher
step limit than an ordinary chat exchange, since a single conflicted file
routinely costs several tool calls on its own, and it shares the same
per-repository run slot as chat and the commit explanation, so none of the
three can run at the same time for one repository.

The resolver is given its own set of tools, in addition to the read tools
also available to chat. It does not get the chat's write tools — its own
tools below are the only way it can affect the repository:

- Listing the files still in conflict and how many conflicting regions each
  one has.
- Reading one specific conflicting region: the common ancestor's version,
  each side's version, and the surrounding lines.
- Replacing one conflicting region with a resolved version, containing no
  conflict markers.
- Marking a file as resolved, which is refused while any conflict marker
  remains in it.

Every one of these tools checks that the file it is asked to touch is
actually one of the conflicted files belonging to the operation the run was
started for — a merge, a rebase (one run per conflicting step) or a
cherry-pick; if that operation's fingerprint (its kind plus the commit being
combined, or, for a rebase, the commit currently being replayed) has changed
since the run began — finished, aborted, or replaced by a different one, or
a rebase that has moved on to its next step — the tools refuse and tell the
model to stop rather than silently acting on an unrelated file or an
unrelated conflict. A file with no conflict markers at all — a binary file,
or one side deleting what the other modified — is reported separately as
something only a human can settle, and the resolver is told to leave those
alone.

The resolver is instructed to work through every conflict it can on its own
without asking the user questions, since nothing it does is final: it can
only edit files and stage them, never commit or otherwise conclude the
operation, and the user reviews its work before anything is committed. It is
told to prefer a resolution that keeps the intent of both sides where
possible, to write nothing that appears in neither side, and to leave a
region alone and say so when it cannot tell which resolution is right,
rather than guess. What counts as "both sides" depends on the kind: for a
rebase the base being rebased onto is already final and the commit being
replayed is re-applied on top of it, and for a cherry-pick the current
branch is final and the picked commit's intent is applied on top. These
kind-specific instructions are appended by the application after the
user-editable prompt, so editing the prompt cannot remove them. When the run
ends, the application appends its own independent summary of what git
reports is still conflicted or still needs a human, regardless of what the
model's own closing message claims, so the displayed outcome cannot
overstate what was actually resolved.

## Prompts

Each of the five actions — chat, explaining a commit, explaining lines of a
file, drafting a commit message, and resolving conflicts — has its own prompt:
fixed instructions combined with a few details of the moment (the repository's
name, its location, the current branch, today's date) before being sent to the
model. Every prompt ships with a built-in default. A user can open the folder
these prompts live in, edit any of them as plain text, and have their own text
used in place of the default from then on; an unmodified or missing file falls
back to the built-in default. Any prompt can be reset back to its default
individually.

## Local model download

A local-provider model that is not yet installed can be downloaded from
settings. Downloading reports progress as it happens — a status phase (for
example, downloading a particular layer), and how many bytes have completed
out of the total, when the source reports a total at all — throttled so that
identical, rapidly repeating progress updates do not flood the interface. A
download in progress can be cancelled; cancelling and any other failure both
end the download and are reported distinctly, so the interface can tell "the
user cancelled this" apart from "this failed." Only one download runs at a
time; starting another while one is already running is refused.

## Rules

1. AI features have three independent providers to choose from: one local,
   two hosted; the chat/agent role and the task role are configured
   separately, each with its own provider and model.
2. A hosted provider's API key lives only in the operating system's own
   secret store; it is never written to the application's own settings and
   never sent back to the interface once saved.
3. An action that needs a hosted provider with no key stored fails
   immediately, before any network call, with a message naming the
   provider.
4. An ordinary chat run's write tools never run unconfirmed: every one pauses
   for an approval card, and nothing destructive (reset, discard, delete a
   branch, amend, drop/pop/apply a stash, force-push, rebase) is offered as a
   tool at all. A commit explanation started from the log has no write tools,
   only the read tools.
5. Only one AI run can be active per repository at a time, shared across
   chat, commit explanation and conflict resolution; a pending write card
   shares that same one-run-per-repository slot.
6. The conflict resolver can edit and stage files but never commits or
   otherwise concludes the operation; the human reviews and finishes it. It
   has no access to the chat's write tools.
7. Every mergetools call re-validates that its target file belongs to the
   operation the run was started for — the same kind and commit (for a
   rebase, the same step) — and refuses otherwise.
8. The final report of a conflict-resolution run is git's own account of
   what remains, not the model's claim.
9. Every prompt has a built-in default; a user override replaces it only
   while a non-empty custom file exists, and can be reset back to the
   default at any time.
10. Only one model download runs at a time per application instance, and it
    can be cancelled without being treated as a failure.
11. Approving a write re-checks the repository's refs and `HEAD` (and, for a
    commit, its staged paths) against what the proposal was built from;
    anything changed since refuses the write rather than running it against
    a state the user never actually approved.
12. Once a write call within one model reply does not end in success, every
    later write call in that same reply is refused before a card is even
    built; a later reply is unaffected.

## Known divergences

The conflict resolver's trigger has no readiness gate at all — it is enabled
purely by there being unresolved conflicts and nothing else running.

None found for the write tools described above: the built behaviour matches
the design document that introduced them.
